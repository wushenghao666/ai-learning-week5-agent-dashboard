## 本周目标

第四周我完成了一个可以保存状态、按依赖执行任务并生成复盘的学习 Agent。命令行能够完成整个流程，任务状态主要通过文本和 JSON 文件观察。本周沿着第四周末尾的计划继续，把 Agent 做成一个本地可视化 Web 应用。

我希望页面能完成四件事：输入学习目标并创建计划，看到任务之间的依赖关系，逐步执行当前可以运行的任务，查看完成率和工具调用过程。项目目录为 `ai-learning-week5-agent-dashboard`，代码、测试和博客副本都放在第五周项目仓库中。网站博客暂时只在本地写入，没有推送到 GitHub Pages。

## 学习内容

### 从命令行 Agent 到 Web 应用

命令行适合验证执行逻辑，浏览器适合持续观察状态。Web 应用需要处理请求、返回数据、管理页面状态和显示错误。我选择 Python 标准库的 `ThreadingHTTPServer`，把服务端和第四周代码放在同一个项目中。这样可以继续使用现有的 Planner、Session、Task、Event 和工具注册表，新增部分集中在 `src/web.py`。

页面启动后由服务端提供 `index.html`、`app.js` 和 `styles.css`。浏览器通过四个接口与服务端交互：`GET /api/session` 读取会话，`POST /api/init` 创建计划，`POST /api/run` 执行任务，`POST /api/reset` 清空会话。接口返回结构化 JSON，前端根据返回结果重新渲染页面。

### API 层和已有执行器的连接

我把 Web 层控制在很薄的一层。创建计划时，接口读取目标文字，调用第四周的 `init_session()`，然后返回完整会话。执行下一步时，接口加载 `outputs/session.json`，调用 `run_session()`，保存修改后的会话，再把执行输出和最新状态返回给浏览器。

这种连接方式让页面只关心用户操作和展示，任务依赖仍然由 `Session.ready_tasks()` 判断。页面不会自己判断 t1、t2、t3、t4 的先后顺序。浏览器刷新时重新请求会话文件，任务状态、尝试次数、结果和事件都能恢复。

### 用状态驱动页面

前端维护一个简单的 `state.session` 对象。每次接口响应到达后，`render()` 根据任务状态更新指标、任务卡片、时间线和复盘建议。任务卡片显示任务编号、标题、动作、工具、前置任务、尝试次数和结果。

状态颜色对应四种任务状态：pending 表示等待执行，running 表示正在处理，done 表示工具调用成功，failed 表示两次尝试都失败。颜色只承担快速识别作用，文字徽标仍然显示完整状态。页面将最新事件放在时间线顶部，事件中的输出或错误都来自会话记录。

### 指标从会话数据中计算

完成率继续使用已完成任务数除以任务总数。工具成功率继续使用成功事件数除以工具调用事件数。页面额外显示当前可执行任务数量和事件总数，帮助我判断当前计划处在哪个阶段。

这些指标由服务端的 `review()` 计算后随会话返回，浏览器只负责格式化百分比。这样命令行复盘和网页复盘使用同一个计算来源，页面不会出现一套独立的统计逻辑。

### 本地 Web 服务的边界

项目定位是单用户本地工具。服务只监听 `127.0.0.1`，数据写入项目的 `outputs/session.json`，没有登录系统，也没有把目标发送到外部服务。页面默认使用规则规划器，第四周留下的 `--llm` 命令仍然可以在有 API Key 时调用模型规划，Web 页面暂时没有加入模型配置入口。

这个边界让我先把界面、接口和状态恢复做完整。以后增加真实模型时，可以在 `/api/init` 中加入明确的规划模式字段，再复用第四周已有的回退逻辑。

### 创建并执行一个计划

我在项目目录运行：

```powershell
python -m src.web
```

浏览器打开 `http://127.0.0.1:8000` 后，输入本周学习 Agent，安排 6 小时并完成一个检索练习，点击创建学习计划。页面显示四张任务卡片：明确本周目标、建立学习清单、安排时间预算、生成复盘提醒。卡片中可以看到依赖关系，只有 t1 没有前置任务。

第一次点击执行下一步后，t1 变为已完成，完成率显示为 25%，可执行任务变成 t2。再次点击后，t2 完成，页面把 t3 释放出来。继续点击两次，t3 和 t4 依次完成，完成率变为 100%。每次操作都新增一条工具调用事件，刷新浏览器后页面仍然显示相同进度。

t3 使用 `time_budget` 工具读取目标中的 6 小时，结果显示为总计 6 小时，建议分为 3 天，每天约 2.0 小时。t4 使用 `review_prompt` 工具生成复盘提醒。页面的时间线完整保留了这四次调用的时间、工具、状态和输出。

### 接口检查

我用 Python 标准库写了一个简单的请求检查，确认服务启动后可以完成以下流程：

1. `GET /api/session` 在没有会话文件时返回空状态。
2. `POST /api/init` 拒绝空目标，正常目标会创建四个任务。
3. `POST /api/run` 每次只执行当前满足依赖的任务。
4. `GET /api/session` 能读回最新状态和复盘指标。
5. `POST /api/reset` 删除会话文件，页面恢复空状态。

前端还检查了空目标提示、没有会话时的执行提示、失败错误显示和窄屏布局。窄屏下任务列表与时间线改为单列，手机宽度也可以阅读。

项目保留第四周的五个单元测试，覆盖规划依赖、会话恢复、复盘指标、小时数校验和模型规划回退。测试命令如下：

```powershell

```

测试结果为 5 个测试全部通过。手动启动 Web 服务后，我完成了创建计划、连续四次执行、刷新恢复和清空会话四个检查。页面显示的完成率、工具成功率和事件数量与 `outputs/session.json` 中的内容一致。

### 这次实现遇到的问题

第一次把 Session 直接交给 `json.dumps` 时，响应无法序列化。`Session`、`Task` 和 `Event` 都是数据类，接口需要把它们转换为字典。我在 `session_payload()` 中提供了统一的转换函数，再附加复盘结果和可执行任务编号，页面收到的数据结构保持稳定。

另一个问题出现在执行按钮。创建计划后如果连续点击，浏览器可能同时发出多个请求。当前服务端每次都重新读取文件，执行结果仍然经过依赖检查；前端提示会随着最后一次响应更新。后续可以增加按钮禁用和请求编号，让并发点击的反馈更清楚。

还有一个细节是静态文件路径。服务端只允许从项目的 `web` 目录读取文件，接口路径以 `/api/` 开头时单独处理。页面资源和会话接口分开后，浏览器刷新不会把静态文件请求误认为 API 请求。

## 本周真正理解了什么

这周让我理解了 Agent 页面化后的核心工作仍然是状态管理。规划器负责生成任务，执行器负责调用工具，会话负责保存事实，Web 层负责把这些事实变成可操作的界面。页面的价值在于把任务依赖、执行边界和复盘指标集中显示出来，使用者可以在每一步确认结果。

我也看到了接口边界的作用。`/api/run` 没有重新实现任务循环，前端没有复制依赖判断，指标没有在 JavaScript 中重新计算。每个模块都保留第四周已经验证过的职责，新增的页面围绕已有会话格式工作。

第五周的目标已经完成：第四周的本地 Agent 现在有一个可以运行的可视化 Web 应用，创建计划、逐步执行、查看事件和刷新恢复都能在浏览器中完成。后面我会继续加入人工确认和任务编辑，让计划在执行前可以被调整，再比较规则规划与模型规划生成的任务结构。

### 线上版本的部署方案

在本地版本稳定后，我把部署拆成前端和后端两部分。GitHub Pages 发布 `web/` 目录，Render 运行 Python API 服务。页面通过 `web/config.js` 读取后端地址，GitHub Actions 发布前由仓库变量 `AGENT_API_BASE` 写入这个地址。

真实模型规划通过页面中的开关触发。后端读取 Render 环境变量 `OPENAI_API_KEY`，调用 Responses API 生成任务草案，再复用项目已有的工具白名单和依赖校验。浏览器只发送学习目标和模式标记，页面代码中没有 Key。没有配置 Key 时，接口返回模型不可用提示，规则规划仍然可以在关闭开关后使用。

这个部署结构让 GitHub Pages 负责稳定发布静态页面，后端承担会话文件、Agent 执行和模型请求。后续接入登录和限流时，可以在后端继续增加用户隔离和用量统计。
